
## Лабораторная работа №13-14. ViewModel и архитектура Android-приложений

## Краткое описание игры
Unscramble Game — это обучающая игра, в которой игроку предлагается угадать исходное слово по его перемешанным буквам. Игра развивает словарный запас и внимательность. За каждый правильный ответ начисляются очки, игра продолжается до тех пор, пока не будут угаданы все слова из заданного списка.

## Технологии
- **Kotlin** — основной язык разработки
- **Jetpack Compose** — современный UI-фреймворк для построения интерфейса
- **ViewModel** — компонент архитектуры для управления состоянием UI
- **StateFlow** — реактивный поток данных для наблюдения за состоянием
- **JUnit** — для модульного тестирования

## Функциональность приложения
- Отображение перемешанного слова
- Поле ввода для ответа пользователя
- Проверка правильности введённого слова
- Отображение счёта и количества угаданных слов
- Индикация ошибки при неправильном ответе
- Возможность пропустить слово
- Диалоговое окно с итоговым счётом по окончании игры
- Возможность начать игру заново

## Контрольные вопросы

### 1. Что такое ViewModel и зачем он нужен?
ViewModel — это компонент архитектуры Android, который предназначен для хранения и управления данными, связанными с UI. Он решает проблему потери данных при изменении конфигурации (например, при повороте экрана). Без ViewModel при повороте экрана активность пересоздаётся, и все данные в ней теряются. ViewModel сохраняет своё состояние при таких изменениях, так как его жизненный цикл привязан к жизненному циклу активности или фрагмента, но он не уничтожается при повороте экрана.

### 2. В чём разница между MutableStateFlow и StateFlow?
- **MutableStateFlow** — изменяемый поток данных, который позволяет обновлять значение через свойство `value`.
- **StateFlow** — неизменяемый поток данных, доступный только для чтения.

**Зачем создавать два поля: _uiState и uiState?**  
Это реализация паттерна "backing property". Приватное поле `_uiState` (MutableStateFlow) доступно только внутри ViewModel для изменения состояния, а публичное поле `uiState` (StateFlow) предоставляется наружу для наблюдения, что гарантирует, что состояние не будет изменено извне.

### 3. Почему в ViewModel нельзя хранить Context или View?
ViewModel имеет более длительный жизненный цикл, чем Activity. Если сохранить ссылку на Context (особенно на Activity), это может привести к утечке памяти, так как ViewModel будет удерживать ссылку на уничтоженную Activity, препятствуя её сборке сборщиком мусора.

### 4. Чем StateFlow отличается от remember и rememberSaveable?
- **StateFlow** — используется для хранения состояния на уровне ViewModel и поддерживает реактивность между ViewModel и UI.
- **remember** — используется внутри Composable-функций для хранения состояния, которое должно сохраняться при рекомпозиции, но теряется при изменении конфигурации.
- **rememberSaveable** — аналогично remember, но сохраняет состояние при изменении конфигурации (например, при повороте экрана).

**Когда использовать?**  
StateFlow — для глобального состояния приложения/экрана. remember — для временного состояния внутри одного Composable. rememberSaveable — когда нужно сохранить состояние UI при повороте экрана.

### 5. Что такое data class в Kotlin и зачем он используется для UI State?
Data class — это класс, предназначенный для хранения данных. Для UI State он используется для создания неизменяемого состояния экрана.

**Какие методы автоматически генерируются для data class?**
- `equals()` / `hashCode()`
- `toString()`
- `copy()`
- `componentN()` (для деструктуризации)

**Зачем нужна функция copy()?**  
`copy()` позволяет создать новый экземпляр класса с изменёнными значениями некоторых полей, сохраняя неизменность (immutability) объекта.

### 6. Как работает collectAsState() в Compose?
`collectAsState()` — это функция, которая подписывается на StateFlow и преобразует его в State<T>. При каждом изменении значения в StateFlow происходит рекомпозиция всех Composable-функций, которые используют это состояние, что автоматически обновляет UI.

### 7. Зачем разделять код на пакеты data и ui?
Разделение на пакеты поддерживает принципы чистой архитектуры (Clean Architecture):
- **data** — содержит модели данных, репозитории, источники данных
- **ui** — содержит UI-компоненты, ViewModel, состояния экрана

Это разделение обеспечивает:
- Чёткое разделение ответственности
- Упрощение тестирования
- Переиспользование кода
- Независимость слоёв друг от друга

### 8. Что происходит с ViewModel, когда приложение полностью закрывается (process death)?
При полном закрытии приложения (process death) ViewModel уничтожается, и все данные теряются. ViewModel не предназначена для долговременного хранения данных.

**Какие альтернативы есть для долговременного хранения?**
- **DataStore / SharedPreferences** — для простых настроек
- **Room Database** — для структурированных данных
- **SavedStateHandle** — для сохранения состояния при process death (используется с ViewModel)
- **WorkManager** — для фоновых задач
- **File storage** — для файлов
